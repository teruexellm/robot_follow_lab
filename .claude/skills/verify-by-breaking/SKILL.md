# つまづきを検査に変える

## なぜ文章では足りないのか

**これは精神論ではなく観測である。**

ある ROS 2 プロジェクトで、踏んだ問題を 99 項目の記録に残した。
そのうち **17 箇所に「2 回目」「3 回目」「2 回踏んだ」と書いてある。**
**書き留めたのに、同じ失敗を繰り返した。**

一方、検査スクリプトに変えた項目は再発していない。
**再発が止まったのは記録したときではなく、実行可能な検査にしたとき。**

だから「気をつける」で終わらせない。手順はこうなる。

    踏む -> 原因を書く -> 検査に変える -> 壊して落ちることを確かめる

最後の一手を飛ばすと、検査自体が動いていないことに気付けない（後述）。

## 1. 検査に変えられる形に落とす

すべてが機械化できるわけではない。**できるものを見分ける。**

| 機械化しやすい | 例 |
|---|---|
| 参照が解決するか | ドキュメントのパス・リンク・節番号が実在するか |
| 設定が届くか | 環境変数がコンテナまで到達しているか |
| 書き方が復活していないか | 禁じたイディオムが再び現れていないか |
| 一覧の取りこぼし | 追加したファイルが索引に載っているか |
| 不変量 | 正常なら必ず変化する量が変化しているか |

| 機械化しにくい | どうするか |
|---|---|
| 「書いた手順を実際に実行したか」 | 定期的に clean clone で通す。完全には塞げない |
| 設計判断の妥当性 | 判断の根拠を記録に残す |

**正直に言うと、最も繰り返したのは機械化しにくい側だった。**
上の 17 箇所のうち 3 回繰り返した項目は「書いた手順を実行していない」で、
これだけは検査にできていない。

## 2. 検査は必ず壊して確かめる

**書いた検査が機能している保証はない。** 実例:

- ドキュメントの参照を調べる検査が、**行継続 `\` をまたげず**
  壊した版を OK と判定した。畳んでから見るよう直した。
- 補助スクリプトが `AttributeError` で**追加以来一度も動いていなかった。**
  死んでも全体は動くので、失敗が成果物にも検査結果にも現れなかった。

手順は毎回同じ。

    1. 正しい状態で OK になることを見る
    2. わざと壊して NG になることを見る
    3. 戻して OK に戻ることを見る

2 を飛ばした検査は、通っていても何も保証しない。

## 3. 黙って skip させない

入力が無いときに静かに成功する検査は、**無いより悪い。**

実例: 「6 種類の検査が通っている」と報告していたが、実際に通っていたのは
4 種類だった。2 つは入力ファイルが環境に無く、
片方は `ERROR` を出して、もう片方は `skip` と出して、
**どちらも全体の結果には影響していなかった。**

- 入力が無いのが**異常**なら、落とす
- 入力が無いのが**正常**なら（生成物が未作成など）、skip と**明示して**
  数に数えない。「全部通った」と読めてはいけない

## 4. 利用者と同じ経路で実行する

**自分の実行経路と利用者の実行経路は違う。**

実例: 検査を `docker run -v $PWD:/workspace ...` で動かしていた。
全ファイルがマウントされるので通る。
利用者が使う `make test` は `compose` 経由で、マウントは成果物だけ。
**通るはずがなかった。**

- 検査は `make test` のような**利用者が叩く入口**から動かして確かめる
- 区切りごとに **clean clone** して通す。
  この原則で見つかった不具合が 4 件あった（空ディレクトリ、
  生成物を前提にした検査、環境変数の未伝達、案内した手順の失敗）

## 5. 「良い数字」を信用しない

異常が「何も起きない」形で出るとき、指標は**良くなることがある。**

実例: 起動に失敗して両機が動かなかった run が、
RMSE 0.2 / 検出率 1.0 / 衝突 0 という過去最良の数字を出した。
静止した対象を正しく検出し続けるため。

**正常なら必ず変化する量**を検査に入れる（この例では走行距離）。
品質指標ではなく、**測れていることの証拠**を見る。

## 6. 同じ信号が正常時にも出るなら、件数を書く

「このエラーは無視してよい」とだけ書くと、**本当に異常なときにも
無視される。**

実例: あるエラーは「意図して止めた」ことの記録で、
**うまく動いているほど増える**（0 件 = 動いていない、14 件 = 良好）。
同じメッセージが異常時には毎秒出ていた。

正常時の実測件数を併記して初めて、文書が判断に使える。

## 実装例

同じリポジトリの `scripts/check_*.py` が実例。
それぞれ冒頭に**どの失敗を機械化したか**を書いてある。

| スクリプト | 防いでいる失敗 |
|---|---|
| `check_docs.py` | 存在しないコマンド・パス・リンクを案内する |
| `check_devlog.py` | 記録の索引ずれ、参照切れ、消える場所への参照 |
| `check_compose_env.py` | 環境変数がコンテナに届かない |
| `check_launch_bool.py` | 真偽値を黙って false に倒す |
| `check_launch_cleanup.py` | 子プロセスの取りこぼし |
| `check_make_image.py` | 編集が反映されないまま古いコードが走る |
| `check_spec_refs.py` | 仕様書に無い節を参照する |
| `check_ai_on_demo.py` | 学習時の検証では出ない誤検出 |

`run_tests.sh` が入口で、`make test` から呼ばれる。

## この型の限界

出どころは **1 プロジェクト・1 環境**である。
他所で同じ比率で効く証拠は無い。
**検査を増やすこと自体が目的化すると、実行時間と保守の負担になる。**
踏んだ失敗に対してだけ足すこと。
