# 推論が遅い / 学習したのに実機で当たらない

## 実行環境

| 症状 | 原因 | 詳細 |
|---|---|---|
| onnxruntime が CPU を食い尽くす | cgroup の CPU 制限を無視して 128 スレッド作る | `DEVLOG E-2` ★ |
| `ros2 run` した推論ノードが venv を見ない | console script はシステム python で動く | `DEVLOG E-3` ★ |
| ONNX 書き出しが `onnxscript` を要求する | torch 2.14 の既定エクスポータ | `DEVLOG E-1` |

## 学習と実機のギャップ

**validation が満点でも実機で当たらないことがある。** この題材で最も
時間を使った領域。

| 症状 | 原因 | 詳細 |
|---|---|---|
| 方位に系統的バイアス（val 1.5 deg / 実機 6.5 deg） | 学習 world と実行 world の外観差。CNN が背景レイアウトに依存していた | `DEVLOG X-1` ★ |
| 何も無い壁を対象と誤検出し続ける | 学習データに実行環境の negative が無い | `DEVLOG X-3` |
| 方位誤差があると LiDAR 融合が背後の壁を拾う | 融合の前提が崩れる | `DEVLOG X-2` ★ |

**対処の型**

1. **学習 world の外観を実行 world に揃える。** 姿勢・照明・配置の
   ランダム化は維持しつつ、部屋の寸法や色は合わせる（X-1）。
2. **実行環境の実画像で誤検出を検査するゲートを別に持つ。**
   学習データ由来の validation では絶対に捕まらない。
   この題材では `data/demo_eval`（実環境 257 枚）での掃引で動作点を決めた。
3. **動作点は学習設定とセット。** 学習量を減らすと、同じ閾値で
   recall が先に死ぬ。実測: 2000 枚/20 epoch は PASS、500 枚/10 epoch は
   精度ゲートを通るのに実環境検査で recall 0.889 < 0.95（`DEVLOG S-25`）。

## データ生成

| 落とし穴 | 詳細 |
|---|---|
| `gz service` CLI はプロセス生成で 20 倍遅い | `DEVLOG D-1` ★ |
| 高速化が stale frame レースを露出させた | `DEVLOG D-2` ★ |
| 相互検証は「どちらが正確か」を決めないと正常を異常と判定する | `DEVLOG D-3` |
| 「判定不能」を negative に押し込むと誤ラベルになる | `DEVLOG D-4` |

## タスクの難易度を先に測る

この題材では、objectness（居るか居ないか）は**自明に解けた**。
AI と色抽出の差は検出率ではなく「部分可視での頑健さ」に出た。
`DEVLOG A-4`

**何を学習させるかを決める前に、そのタスクが自明でないかを確かめる。**
自明なタスクで AI の優位を示そうとしても差が出ない。
