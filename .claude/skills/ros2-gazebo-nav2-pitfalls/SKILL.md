# ROS 2 / Gazebo / Nav2 の落とし穴

## これは何か

`robot-follow-lab`（ROS 2 Jazzy + Gazebo Harmonic + Nav2 + ONNX、CPU のみ）を
実装する過程で実際に踏んだ問題の索引。**症状から引く**ように並べてある。

詳細は同じリポジトリの `DEVLOG.md` にある。各項目は
**症状 → 発見経緯 → 原因 → 対処 → 再発防止**の形で、多くは実測値つき。
この索引は引くためのもので、中身を複製しない。
`DEVLOG N-16` のような参照をそのまま検索すれば本文に当たる。

## 使い方

症状で当たりをつけて、該当ファイルを読む。

| 症状 | 見るファイル |
|---|---|
| ノードが固まる / 起動が終わらない / lifecycle が active にならない | `lifecycle-and-startup.md` |
| パラメータが効かない / launch 引数が無視される / TF 名がおかしい | `launch-and-params.md` |
| ロボットが動かない / センサに何も映らない / 車体の姿勢が変 | `control-and-sensors.md` |
| コンテナで動かない / 権限 / 依存が壊れる / discovery しない | `container-and-build.md` |
| 記録が取れない / 計測値が信用できない / 速度が出ない | `recording-and-measurement.md` |
| 推論が遅い / 学習したのに実機で当たらない | `inference-and-training.md` |

## 読むときの前提

- **出どころは 1 プロジェクト 1 環境**（4 コア CPU / llvmpipe ソフトウェア
  レンダリング / RTF 0.75 前後）。フレームワークの挙動に起因する項目は
  そのまま効くはずだが、**数値は環境依存**である。鵜呑みにせず測ること。
- 「★」は特に時間を溶かしたもの。
- **同じ症状が正常時にも出ることがある。** 件数やレートを見ないと
  判断できない項目が複数ある（例: `recording-and-measurement.md` の
  「意図した halt が ERROR として記録される」）。

## 共通する形

個別の原因は違うが、繰り返し出た構造が 3 つある。

1. **応答の取りこぼし** — `change_state` / `navigate_to_pose` の応答が
   起動直後の負荷で落ち、呼んだ側が永久に待つ。3 か所で起きた
   (`DEVLOG` N-13 / N-16 / S-30)。**非同期 API は「要求 → 受理 → 結果」の
   3 段すべてを数え、待ちには必ず上限を置く。**
2. **黙って既定値に倒れる** — 届かない環境変数、解釈できない真偽値、
   死んでも誰も困らない補助プロセス。**異常が「何も起きない」形で出る。**
3. **計測系が被験体を変える** — 記録の負荷、残留プロセスの CPU 消費。
   **「速度が出ない」ときは資源の奪い合いを先に疑う。**
