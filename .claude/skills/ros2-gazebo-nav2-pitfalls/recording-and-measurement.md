# 記録が取れない / 計測値が信用できない

## 計測系そのものが結果を変える

| 症状 | 原因 | 詳細 |
|---|---|---|
| 追従性能が落ちる | Python で書いた bag recorder の負荷 | `DEVLOG S-10` |
| 学習がなんとなく遅い | 前の工程の `gz sim` が残って CPU を食う | `DEVLOG S-19` |

**「速度が出ない」ときは、計算資源を誰かが持っていっている可能性を先に
疑う。** この題材では、負荷の出どころを押さえないまま制御側を 3 回直して
いずれも効かなかった（`DEVLOG T-7` / `T-8` / `T-9`）。

## 記録できない

| 症状 | 原因 | 詳細 |
|---|---|---|
| `ros2 bag record` がトピックを拒否 | 「複数の型が結び付いたトピック」は記録できない | `DEVLOG S-9` |
| 終了時にまとめて書くファイルが間に合わない | 終了前に読む相手がいる | `DEVLOG V-5` |

## 「良い数字」が測れている証拠にならない

**最重要。** 起動に失敗して誰も動かないと、

    follow_rmse_m 0.2 / target_detected_fraction 1.0 / collision_count 0

という**最良に見える数字**が出る。静止した対象を正しく検出し続けるため。
`DEVLOG S-30`

**対処の型** — 正常なら**必ず変化する量**を検査に入れる。
ここでは走行距離（`leader_path_m`）。0 ならその run の指標は読めない。

## 同じメッセージが正常時にも異常時にも出る

`Failed to get result for follow_path in node halt!` は、BT が意図して
`FollowPath` を止めたときに Nav2 が記録する ERROR。**追従できているほど
増える。** 実測（90 s）:

    起動失敗（誰も動かない）  0 件
    marker（検出率 0.54）     9 件
    ai    （検出率 0.89）    14 件

一方、同じメッセージはゴール送り直しの異常時には毎秒出ていた。
**深刻度では判断できない。件数とレートを見る。** `DEVLOG S-31`

**Nav2 は「意図して止めた」場合も ERROR として記録する。**
ERROR の有無で正常・異常を切り分けようとすると誤る。

## 計測の設計

| 落とし穴 | 詳細 |
|---|---|
| `spin_once(timeout_sec=T)` で回数ループするとペーシングが壊れる | `DEVLOG M-1` ★ |
| 計測窓が起動直後の過渡状態に重なる | `DEVLOG M-3` |
| 診断ノードに `use_sim_time` を設定し忘れる | `DEVLOG M-4` |
| latched トピックを volatile QoS で購読して「データなし」と判断 | `DEVLOG M-5` |
| 静止シーンで測って「定数出力」と誤診する | `DEVLOG M-6` ★3 回踏んだ |
| `ros2 topic echo` が配列を既定 128 要素で切り詰める | `DEVLOG S-6` |
| `ros2 topic hz` は実時間。sim 時間ではない | `DEVLOG` の実測の節 |

**非同期 API は「要求 → 受理 → 結果」の 3 段すべてを数える。**
受理までしか見ない計器は「正常に見える故障」を作る（`DEVLOG T-3`）。
